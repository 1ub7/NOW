# 프로젝트가 진행 되는 방법/순서
## 1. 프로젝트 진행 순서
**기획**    
프로젝트의 방향과 목표를 정하는 단계    
(프로젝트 전체의 뼈대를 만드는 과정)
- 주제 선정
- 어떤 기능 만들지 결정
- 프로젝트 범위 정하기
- 일정 대충 정하기

-> 결과물   
- 기능명세서
- 역할 분배표
- 프로젝트 소개

**설계**    
프로젝트를 실제로 어떻게 구현할지 전체 구조를 설계하는 단계    
(프론트엔드, 백엔드, 데이터베이스 구조를 구체적으로 설계)
- 화면 
    - 사용자 화면의 구조를 설계하는 과정
    - ex) 페이지가 어떻게 구성되는지, 메뉴가 어디에 위치하는지
    - 사용도구 : Figma, draw.io
- DB 
    - 데이터를 어떻게 저장할지 설계하는 과정    
    (테이블 구조와 관계를 정의함)
    - 설계하는 내용 : 테이블 구조, 컬럼 종류, PK/FK, 테이블 간 관계
- API (프론트와 백엔드 연결 규칙 작성)   
    - HTTP Method
    - URL(Path)
    - Request
    - Response
    - Status Code

---

**협업 세팅**   
- **Git Repository 생성**   
프로젝트 코드를 저장하고 버전을 관리하기 위한 저장소 생성
- **브랜치 규칙 정하기**    
각자 작업 공간을 나누기 위해 브랜치 전략을 정함
- **역할 분배**     
팀원별 담당 영역을 나눔
- **커밋 규칙 정하기**  
커밋 메시지 형식을 통일함

----

**개발**    
실제로 기능을 구현하는 단계   

---

**테스트**  
프로젝트의 오류와 문제점을 찾는 단계
- 기능 테스트   
기능이 정상적으로 동작하는지 확인함
    - 로그인 되는지
    - 글 작성 되는지
- 예외 처리     
비정상적인 입력 상황을 확인
    - 빈 값 입력 시에 어떻게 되는지
    - 서버 오류 발생 시 어떻게 처리되는지
- UI 테스트     
화면이 정상적으로 출력되는지 확인
    - 모바일 안 깨지는지    

----

**배포**    
개발한 프로젝트를 실제 서버에 올리는 단계   
(사용자가 직접 접속할 수 있는 상태로 만드는 과정)
프로젝트 빌드   
↓   
Docker 이미지 생성  
↓   
EC2 업로드  
↓   
컨테이너 실행   
↓   
Nginx 연결  
↓   
도메인 연결     

---

**유지보수**   
배포 이후에 프로젝트를 관리하는 단계 
- 버그 수정     
사용 중 발견된 오류 수정
- 기능 추가     
새로운 기능을 개발함
- 성능 개선     
속도와 효율을 향상시킴
- 서버 모니터링     
서버 상태를 지속적으로 확인

## 2. 프로젝트 진행 방법
**회의 진행**   
프로젝트 시작 전에 팀원끼리 회의함  
- 프로젝트 주제
- 필요한 기능
- 개발 일정
- 역할 분배

등을 정함

----

**문서 작성 후 공유**   
설계 내용을 문서로 정리하고 공유함  

작성하는 것      
- 기능명세서
- API 명세서
- ERD
- 와이어프레임

사용하는 것
- Notion
- Google Docs

---

**Git 기반 협업**   
Git으로 각자 작업 관리함

순서
- 기능별 브랜치 생성
- 각자 기능 개발
- commit 후 push
- Pull Request(PR) 생성 후 코드 병합

---

**역할별 개발 진행**    
각자 맡은 영역을 개발함     
(아래는 예시로 적음)    
**프론트엔드**  
- 화면 제작
- API 연결 및 UI 구현

**백엔드**      
- API 개발
- DB 연결
- 비즈니스 로직 구현

**데브옵스**    
- Docker 설정
- 서버 세팅
- 배포 자동화

---

**정기적인 공유 및 피드백**     
개발 진행 상황 공유함   
보통 확인하는 것    
- 어디까지 개발됐는지
- 오류 있는지
- 일정 밀리는지

---

**테스트 진행**     
기능이 정상 동작하는지 확인함   
테스트 방식     
- 직접 실행
- Postman 테스트
- 팀원끼리 교차 테스트

확인하는 것     
- 기능 정상 동작 여부
- 예외 처리 여부
- UI 오류 여부

---

**버그 수정 및 최종 정리**      
테스트 중 나온 문제 수정함  
하는 것 
- 버그 수정
- 코드 정리
- README 작성
- 발표 준비

----

**서버 배포**   
프로젝트를 실제 서버에 올림     

----

**유지보수 및 업데이트**    
배포 후 수정 및 기능 추가 진행함    
**ex)**
- 버그 수정
- 기능 개선
- 서버 모니터링

## 3. 명세서
**명세서란?** 어떤 기능이나 구조를 정확하게 정의해놓은 문서
### 3-1. 기능명세서
----
**기능명세서란?** 프로젝트에 어떤 기능이 존재하는지 정리한 문서     
(서비스에서 제공하는 기능의 목적과 동작 방식을 미리 정의하기 위해 작성함)

**왜 작성해야함?** 없으면 아래와 같은 일들이 발생함     
- 팀원마다 기능 이해가 달라짐
- 개발 범위가 계속 증가함
- API 구조가 꼬임
- 역할 분배가 어려워짐

**들어가는 내용?**      
| 항목 | 설명 |
| ----- | ----- |
| 기능명 | 기능 이름 |
| 설명 | 기능 동작 설명 |
| 입력값 | 사용자가 입력하는 데이터 |
| 출력값 | 결과 데이터 |
| 권한 | 사용 가능한 사용자 |
| 상태 | 개발 여부 |

### 3-2. API 명세서
----
**API 명세서란?** 프론트엔드와 백엔드가 어떻게 데이터를 주고받을지 정의한 문서  
(서버와 클라이언트의 대화 규칙 설명서)  

여기서 **API란?** 프로그램끼리 데이터를 주고받기 위한 인터페이스(연결 규칙)

**왜 작성해야함?**      
- 프론트와 백엔드 연결 기준이 필요하기 때문
- 협업의 효율성을 증가 시키기 위함
- 유지보수가 쉬워짐
- 테스트의 기준이 됨

**들어가는 내용**   
| 항목 | 설명 |
| ----- | ----- |
| Method | 요청 방식 |
| URL(Path) | API 주소 |
| 설명 | API 기능 설명 |
| Request | 클라이언트 요청 데이터 |
| Response | 서버 응답 데이터 |
| Status Code | 응답 상태 |
| Authorization | 인증 필요 여부 |

### 3-3. 기능 명세서와 API 명세서 차이점
---
| 구분 | 기능명세서 | API 명세서 |
| ----- | ----- | ----- |
| 목적 | 어떤 기능이 존재하는지 정의  | 기능을 어떻게 통신하는지 정의 |
| 설명 대상 | 서비스 기능 자체 | 프론트 ↔ 백엔드 통신 |
| 포함 내용 | 기능 이름, 기능 설명, 권한, 상태 | Method, URL, Request, Response, 상태코드 |
| 예시 | 로그인 기능, 게시글 작성 기능 | POST /login, GET /posts |
| 중점 | 기능의 존재와 동작 | 데이터 통신 규칙 |
| 결과 | 어떤 서비스를 만들지 정리 | API 호출 방식 정리 |

## 4. QA
**QA(Quality Assurance)란?** 프로젝트가 정상적으로 동작하는지 품질을 검증하는 과정

**왜 QA를 함?** 개발이 끝났다고 바로 배포를 하면 오류들이 뜰 수도 있음      
-> 정상 동작하는지 한번 더 점검하는 과정

**하는 것** 
- **기능 테스트**    
기능이 제대로 동작하는지 확인
    - 로그인 되는지
    - 게시글 작성 되는지
    - 댓글 등록 되는지
- **예외 처리 테스트**      
이상한 입력 넣어서 확인
    - 빈 값 입력
    - 비밀번호 틀림
    - 존재하지 않는 게시글 접근
-  **UI 테스트**    
화면이 정상인지 확인
    - 모바일 화면 안 깨지는지
    - 버튼 위치 이상 없는지
    - 글자 안 겹치는지
- **서버 테스트**   
서버 오류 확인
    - API 정상 응답 여부
    - 상태코드 확인
    - 서버 다운 여부

## 5. 릴리즈
**릴리즈(Release)란?** 개발한 프로젝트를 실제 사용자에게 공개하는 과정  
(서비스를 배포해서 사용 가능하게 만드는 것)

**왜 중요함?**     
- 사용자가 실제로 사용할 수 있게 됨
- 실제 운영 환경에서 프로젝트 완성도를 확인할 수 있음
- 배포 경험 자체가 중요함
- 유지보수의 시작점이 됨

**릴리즈와 배포의 차이?**   
배포 -> 서버에 올리는 작업
릴리즈 -> 사용자에게 공개하는 것

**하는 것**     
- 프로젝트 최종 점검
    - API 정상 동작하는지
    - 서버 안 터지는지
    - 버그 없는지
- 버전 관리     
보통 버전 이름을 붙임
- 서버 공개     
사용자가 접속 가능하게 함
- README 및 문서 정리   
    - 프로젝트 소개
    - 실행 방법
    - 기술 스택
    - API 설명  
    
    정리함

### 5-1. 릴리즈 관련 주요 단어
----
| 단어 | 의미 |
| ----- | ----- |
| Deploy | 서버 배포 |
| Release | 사용자 공개 |
| Version | 프로젝트 버전 |
| Hotfix | 긴급 수정 |
| Patch | 버그 수정 버전 |
| Rollback | 이전 버전으로 복구 |

## 6. CRUD
**CRUD란?** 데이터를 처리하는 4가지 기본 연산
- **C**reate : 생성
- **R**ead : 조회
- **U**pdate : 수정
- **D**elete : 삭제

### 6-1. HTTP의 메서드 매핑
---
CRUD는 HTTP 메서드 설계의 기반이 되어줌 

Create = POST   
Read = GET      
Update = PATCH(PUT)     
Delete = DELETE     

**PUT과 PATCH**     
PUT -> 전체 수정 (리소스 전체 교체)     
PATCH -> 부분 수정 (일부 필드만 변경)   

**멱등성**   
같은요청을 여러 번 보내도 결과가 같으면 멱등성이 있는 것!       
GET / PUT / DELETE -> O     
POST -> X

### 6-2. DB 연산 매핑
---
Create = INSERT     
Read = SELECT       
Update = UPDATE     
Delete = DELETE     

### 6-3. 상태 코드
---
**성공**
- 200 : 조회 혹은 수정 성공
- 201 : 생성 성공
- 204 : 요청 성공(응답 본문 없음)

**클라이언트 오류**
- 400 : 요청 값 이상함
- 401 : 인증 안됨(로그인 필요)
- 403 : 권한 없음
- 404 : 데이터 없음 (ID 틀림)

**서버 오류**
- 500 : 서버 오류 발생(예외 처리 실패)

### 6-4. 특징
---
- 모든 데이터 시스템의 기본 구조
- HTTP 메서드랑 1:1로 매핑됨
- DB 중심 구조가 됨
- REST API 설계의 핵심 기준
- Read(GET)는 데이터를 조회만 하며 서버 상태를 변경하지 않음
